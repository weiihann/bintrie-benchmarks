UBT vs PBT — Locality Sweep

Twelve-cell K-sweep at 75 GB. The original "PBT loses everywhere" result was the product of two compounding problems: a parallel-zone commit implementation that paid two deep-tree copies per block for no parallelism gain, and a --cache 0 flag that disabled the very mechanism PBT relies on. Fix both, and PBT lands at parity with UBT, modestly favored at high-clustering workloads.

01 / HEADLINE

PBT lands at parity with UBT; design works as intended at high clustering.

Final headline: with the parallel-zone code disabled in the PBT geth fork and Pebble's default block cache enabled, the K-sweep produces the shape PBT was designed for. PBT is modestly favored on low-K workloads (more clustering opportunity); marginally slower at K=256 (no clustering to exploit).

02 / DESIGN

What this benchmark probes.

PBT is a single binary trie like UBT; the difference is only in key derivation. UBT uses key = H(addr ‖ slot) — keys randomly distributed across the keyspace. PBT prepends a zone-prefix: key = zone_prefix ‖ H(addr) ‖ slot — a contract's storage stems share the same prefix bytes, so they sit adjacent in Pebble's keyspace. The hypothesis: this clustering should produce fewer cold disk fetches per block when consecutive accesses hit the same contract.

To map where the mechanism wins, we sweep K = the number of distinct contracts touched per block, holding the total work constant at T = 256 stem touches per block. Within each contract, stems are visited in stem-strided order (slot indices 0, 256, 512, …) so each touch hits a different stem — no in-stem reuse muddying the locality signal.

Each cell is a single ~6 M-gas tx in its own block (Osaka tx cap permits one such tx per block; gas limit fixed at 20 M). --dev.period 1 seals the block as soon as the tx is in the mempool. The harness drops OS page cache via sysctl vm.drop_caches=3 between every run for cold inter-run state. Pebble's default block cache is enabled, so consecutive reads of nearby keys within a single block can hit cache.

Now the clustering benefit materializes: PBT 1.07× at sstore_k1, 1.07× at sstore_k10, 1.05× at mixed_k1 — the high-clustering workloads PBT was designed for.

04 / MECHANISM

Where the wins come from.

Geth's slow-block log records a per-block timing breakdown: execution_ms + state_read_ms + state_hash_ms + commit_ms = total_ms. The final-run decomposition makes PBT's clustering visible at low K and shows where it neutralizes at high K.

sstore_k1 (max clustering, peak PBT win at 1.07×)

total35.032.8−2.2

PBT saves time on both disk reads (1 ms) and hashing (2.8 ms). The bigger savings is on hashing — interesting because hashing is CPU work, not I/O. The mechanism: re-hashing a dirty internal node requires loading the node's children to read their hashes. PBT's modified leaves are clustered → their ancestor internal nodes' children are densely packed → Pebble's block cache covers them after the first miss. UBT's modified leaves are scattered → ancestor children are scattered across SSTables → more cache misses inside the hashing path.

At K=256 each touch is on a different contract — no within-block clustering for PBT to exploit. State_read_ms still favors PBT by 8 ms (a per-contract prefix region is still slightly more compact than fully random UBT keys), but PBT pays 11.5 ms more on hashing. At full scatter, PBT's slightly different trie shape costs more than the modest read locality saves.

The honest summary: PBT's clustering produces a workload-shaped advantage. At workloads that touch many slots of a small number of contracts (small K), PBT wins by a few percent. At workloads that touch one slot each across many contracts (K → T), PBT loses by a few percent. The crossover is around K = 100. For realistic mixed workloads — neither pure clustering nor pure scatter — PBT and UBT are at parity, with PBT slightly favored on average.
05 / THE PARALLEL-ZONE BUG

The published loss was an implementation bug.

The PBT geth fork (branch binary/pbt-flat-state) carries a commit titled "core/state: parallel zone updates and binary trie lifecycle tests" that rewrote IntermediateRoot's commit path. The new path splits the trie at depth 0 (zone 000 = accounts, zone 1 = main storage), updates each zone's sub-view concurrently via errgroup, then merges back.

The performance problem: the split and merge each do a recursive deep copy of whatever portion of the trie is loaded into the arena store. Both halves of the trie, on every block — including read-only blocks (gas accounting writes 2-3 leaves into the account zone, so the path is never a no-op). 

// trie/bintrie/trie.go
func (t *BinaryTrie) SplitRoot() (left, right *BinaryTrie, err error) {
    // ...
    leftStore.root = leftStore.copyFrom(t.store, rootNode.left)   // recursive deep copy
    rightStore.root = rightStore.copyFrom(t.store, rootNode.right) // recursive deep copy
}

func (t *BinaryTrie) MergeRoot(left, right *BinaryTrie) {
    rootNode.left = t.store.copyFrom(left.store, left.store.root)   // recursive deep copy
    rootNode.right = t.store.copyFrom(right.store, right.store.root) // recursive deep copy
}

// trie/bintrie/node_store.go
func (dst *nodeStore) copyFrom(src *nodeStore, srcRef nodeRef) nodeRef {
    switch srcRef.Kind() {
    case kindInternal:
        // ... recurse into both children ...
    case kindStem:
        for i, v := range srcStem.values {
            if v == nil { continue }
            cp := make([]byte, len(v))   // allocate per value, every block
            copy(cp, v)
            dstStem.values[i] = cp
        }
    }
}

Two full subtree deep-copies per block. For our K=1 block touching 256 stems, ~300+ in-memory nodes get duplicated twice, every value blob gets make([]byte, len(v)) + copy.

And the parallelism almost never pays it back. Every Ethereum block writes 2-3 leaves to zone 000 from gas accounting (sender nonce, sender balance, coinbase balance). For pure-read blocks: 3 writes, all in zone 000, right worker has nothing to do. For our SSTORE workloads: ~256 writes to zone 1, 3 to zone 000, heavily imbalanced. Two goroutines saving a few ms doesn't recover ~30–70 ms of deep-copy overhead.

The fix: a one-line patch forcing applyBinaryTrieUpdates to fall through to the existing applyBinaryTrieUpdatesSequential sequential path. That single line collapsed PBT's published loss from 0.54 – 0.97× to 0.96 – 1.10× — at parity with UBT. The clustering benefit itself was being smothered under the parallel-zone bookkeeping.

06 / CAVEATS

What this campaign doesn't (yet) establish.

Block size 6 M gas — smaller than mainnet.

Each block is one ~6 M-gas tx (T=256 stem touches × ~22 k gas / touch). That's smaller than typical Ethereum blocks (~30 M+ on Pectra). Smaller blocks amplify whatever per-block fixed overhead exists between configs. At T=700 (16 M gas, the Osaka per-tx cap), the curve would likely compress: both PBT's wins at low K and PBT's losses at K=256 should attenuate.

Workload is cold-insert SSTOREs, not warm-updates.

Our SSTOREs write fresh slot ranges (per-run counter offsets) so every write is cold-init (zero → nonzero). That's the cleanest comparison but it leaves out PBT's strongest theoretical case: re-writing existing leaves under a clustered prefix region, where PBT could share more trie-walk work between writes. A realistic workload with warm-update writes (ERC20 transfers between existing accounts, AMM pool state updates) would likely surface a larger PBT win.

Account-zone benchmarks deferred.

test_account_locality.py exists (BALANCE-read and value-transfer parametrized by K) but account_transfer hangs geth at 10 GB RSS under high-frequency value-transfer workloads on both UBT and PBT — unrelated to the PBT design, but blocks the account sidecar. Filed for follow-up.

Single DB size (75 GB).

The disk-read clustering benefit should scale roughly linearly with DB size (UBT's random stems land in more SSTables as Pebble accumulates levels). The hash overhead should stay roughly constant. Extrapolating, PBT's wins should grow at larger scales — 150 GB and 300 GB campaigns are open follow-ups.

07 / VERDICT

What we now know.

The parallel-zone implementation is a clear regression. It hurts every block (deep-tree copy overhead) for almost no parallelism gain (heavily skewed zone activity). Removing it should ship upstream to the PBT geth fork independent of any other decision.

PBT's design works as intended at small block scale and realistic cache config. The clustering mechanism reduces state_read time at all K and state_hash time at low K, where the modified subtree is dense. The wins are modest (~5–7%) on the workloads PBT favors.

The original "PBT loses everywhere" conclusion was wrong. Both the parallel-zone implementation bug and the --cache 0 methodology choice independently suppressed PBT's design benefits. Once both are addressed, the picture flips from "PBT loses 0.54–0.97×" to "PBT at parity, modestly favored on high-clustering workloads."

Provisional recommendation.

The PBT design is worth pursuing, but the case for adopting it on mainnet rests on two open questions: how the result scales to realistic mainnet workloads (block size 16–30 M, warm-update writes, multi-zone activity per block) and how it scales with DB size (the read-clustering benefit should grow at 150 GB+). The next experiments should answer those.
